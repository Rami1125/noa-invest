# מפרט שכבת השליפה — סידור נועה-AI

עודכן: 2 בנובמבר 2026  
מאגר שנבדק: `Saban-94/noa-invest`, ענף `main`  
מטרה: לאפשר לחדר הצ׳אט לענות על שאלות מכל מקורות הנתונים המוגדרים, תוך שמירה על קריאה בלבד, מקוריות הנתונים ועקיבות מלאה.

> זהו מפרט שכבת שרת ושליפה. אין בו שינויי UI/UX ואין בו הרשאה לכתיבה לגיליונות.

## 1. ממצאי בדיקת הקוד הקיים

### מבנה הצ׳אט

- הפרויקט הוא TypeScript עם TanStack Start ו-`createServerFn`; הוא אינו שרת Express/Node עצמאי. נקודת השרת הקיימת לבינה היא `src/lib/ai.functions.ts`, והמסך הראשי הוא `src/routes/chat.tsx`.
- `askNoa` מקבל הודעות שיחה ומספר לקוח אופציונלי. השרת שומר את `API_TOKEN` בצד השרת ומשתמש ב-`GAS_URL` או בכתובת ברירת המחדל.
- `getServerContext` שולף כיום בכל שאלה שמונה מקורות במקביל: `getNotes`, `getOrders`, `getIturanPto`, `getCatalog`, `getGps`, `getCustomers`, `getDashboard`, `getRamiInquiries`. אין בו עדיין ניתוב לפי כוונת השאלה לכל רשימת הטאבים שהוגדרה.
- `getCustomerContext` משתמש ב-`loadCustomerHistory` ומביא היסטוריית לקוח משבעה טאבים.
- `src/routes/chat.tsx` טוען גם תעודות ו-PTO בנפרד למסך. יש להימנע משליפה כפולה של אותם נתונים באותה בקשה.
- `src/components/NoaChatShell.tsx` מכיל כרגע תשובת דמו מקומית (`localNoaReply`) ואינו מחובר ל-`askNoa`. אין להתייחס אליו כמקור מידע מאומת.
- `compactSource` מדרג רשומות לפי הופעת מילות שאלה ומחזיר מספר מוגבל של רשומות, ללא cursor או הוכחה שכל הטווח נסרק. לכן היעדר תוצאה ממנו אינו הוכחה שהרשומה אינה קיימת.

### פערים שיש לטפל בהם לפני הכרזה על חיבור מלא

1. ב-`apps-script/Code.gs` קיים ניתוב ל-`getIturanPto`, אך בקבצי Apps Script שנמצאו במאגר לא נמצאה הגדרת `handleGetIturanPto`. ייתכן שהפונקציה נמצאת בקובץ פריסה שאינו במאגר; יש לאמת בפרויקט Apps Script הפעיל.
2. `src/lib/ituran-api.live.functions.ts` קורא ל-`getIturanVisits`, אך ה-action אינו מופיע ב-switch של `doGet` ב-`apps-script/Code.gs`.
3. `getCatalog` מנותב ב-`doGet` ל-`getCatalog_()`, אך הגדרת הפונקציה לא נמצאה בקובצי Apps Script שבמאגר. הערת הקוד ב-`notes-api.functions.ts` מתייחסת ל-`מילון לוגיסטי`, בעוד המיפוי שנמסר הוא `מילון_לוגיסט`; שם הטאב טעון אימות.
4. `getHarelInquiries`, `getLogisticsAudit`, `getTachograph`, `getCitySummary` ו-`getServerLog` אינם מופיעים כ-actions ב-switch הקיים של `doGet`.
5. קיים action בשם `getLogisticsAuditEvidence` שמחזיר ראיות והחלטות עבור מספר תעודה מסוים. הוא אינו תחליף ל-`getLogisticsAudit` שמחזיר רשומות לבקרה רוחבית.
6. `getCustomerHistory` קיים ב-`Customers.gs`, וגם קיימת טעינה ישירה בצד השרת ב-`customer-history.server.ts`. אלו שני מסלולי שליפה שונים עם צורות תגובה שונות.
7. קיימות שתי הגדרות בשם `handleGetOrders_`: אחת ב-`apps-script/Code.gs` ואחת ב-`apps-script/Orders.gs`. אם שני הקבצים נפרסים באותו פרויקט Apps Script, יש לפתור את ההתנגשות ולבחור מימוש קנוני לפני שינוי או פריסה.
8. `customer-history.server.ts` קורא כרגע טווח קבוע `A1:AZ3000`. אם יש יותר מ-3,000 שורות או עמודות מעבר ל-AZ, הקריאה עלולה להיות חלקית בלי שהצרכן יידע זאת.
9. קוד השליפה הישירה ב-`sheets-integration.ts` כולל גם פונקציות כתיבה ולוג שגיאות. שכבת הצ׳אט החדשה חייבת להשתמש רק במסלולי קריאה ייעודיים ולא לקרוא לפונקציות סנכרון/כתיבה.

הבדיקה נעשתה מול קוד המאגר בלבד. לא בוצעה קריאה לגיליון החי, ולכן לא אומתו כותרות השורות הנוכחיות, מספר הרשומות, הרשאות חשבון השירות או מצב הפריסה הפעילה.

## 3. חוזה API אחיד

הדפדפן אינו שולח שם טאב, טווח A1, שם עמודה או כתובת GAS. הוא שולח שאלה והקשר שיחה בלבד. השרת מסיק intent, בוחר actions מתוך allowlist, ומרכיב את הבקשות בעצמו.

```ts
type RetrievalAction =
  | "getNotes" | "getOrders" | "getIturanPto" | "getIturanVisits"
  | "getCustomerHistory" | "getCitySummary" | "getCatalog"
  | "getRamiInquiries" | "getHarelInquiries" | "getLogisticsAudit"
  | "getTachograph" | "getServerLog";

type RetrievalFilters = {
  customerNo?: string;
  orderId?: string;
  noteId?: string;
  truck?: string;
  driver?: string;
  siteKey?: string;
  city?: string;
  status?: string;
  fromDate?: string; // ISO date
  toDate?: string;   // ISO date
  q?: string;
};

type RetrievalRequest = {
  action: RetrievalAction; // נוצר בשרת מתוך intent; לא מתקבל חופשי מהדפדפן
  filters: RetrievalFilters;
  page?: { limit?: number; cursor?: string };
};

type RetrievalResponse<T> = {
  success: boolean;
  action: RetrievalAction;
  sourceTab: string;
  fetchedAt: string;
  data: T[];
  total: number | null; // null אם המקור אינו מספק total מאומת
  page: { limit: number; nextCursor?: string; hasMore: boolean };
  completeness: "complete" | "partial" | "unknown";
  freshness: "live" | "cached" | "unknown";
  warnings: string[];
  requestId: string;
  error?: {
    code: string;
    message: string;
    retryable: boolean;
  };
};
```

כללים:
- `success: true` עם `data: []` פירושו שהמקור נענה ולא נמצאו רשומות בפילטר. זה שונה מ-`success: false` או `completeness: partial`.
- `sourceTab` הוא שם הטאב בפועל שהשרת קרא, לא רק השם שהתבקש.
- `fetchedAt` הוא זמן השליפה מהשרת. זמן cache יוצג בנפרד ולא יוצג כאילו מדובר בשליפה חדשה.
- `total: null` עדיף על ספירה משוערת.
- אין להעביר ל-AI שורות שלמות אם נדרשים רק מספר מזהה, תאריך, סטטוס ופרטי התאמה.
- `rowNumber` יכול להישמר לצורכי trace פנימיים בלבד; אין להשתמש בו כמזהה עסקי.
- אין לקבל מהלקוח `sheetId`, `tab`, `range`, `token` או שם פעולה שאינו ברשימה.

## 4. ניתוב כוונות בחדר הצ׳אט

| דפוס שאלה | מקורות שיש לשלוף |
|---|---|
| מספר הזמנה / מה פתוח / מה סופק | getOrders |
| תעודה / פרטי תעודה / תעודה חסרה | getNotes + getOrders; לפי הצורך getLogisticsAudit |

| מנוף / PTO / פתיחות מנוף | getIturanPto |
| שהייה / כניסה ויציאה / ביקור | getIturanVisits + getCustomerHistory לפי לקוח/אתר |
| עיר / אזור / קצב ביקורים | getCitySummary |
| מק״ט / מוצר / משקל | getCatalog |
| בירור אצל ראמי | getRamiInquiries |
| אישור מנכ״ל / בירור הראל | getHarelInquiries |
| בקרת תעודה / אסמכתאות | getLogisticsAudit |

אין לשלוף את כל המקורות בכל שאלה. יש לבצע ניתוב לפי intent, ולאחד קריאות לאותו action באותה בקשה. שאלה עמומה תגרום לשליפה מצומצמת של המקור הסביר ביותר, ולא לקריאה גורפת של כל הגיליונות.

## 5. מנוע התאמת הזמנות לתעודות — שלב ראשון

### מודל נתונים מינימלי

```ts
type OrderRecord = {

  customerNo?: string;
  customer?: string;
  date?: string;
  address?: string;
  status?: string;
  noteId?: string;             // מס' תעודת משלוח אם קיים בהזמנה
  itemsText?: string;

  sourceRowKey: string;        // פנימי בלבד
};

type NoteRecord = {
  id: string;                  // מס' תעודת משלוח
  orderId?: string;            // מס' הזמנה מפורש בתעודה
  orderIdIsExplicit: boolean;  // חובה להבחין בין ערך מקור לבין fallback
  customerNo?: string;
  customer?: string;
  date?: string;
  address?: string;
  items?: Array<{ sku?: string; name: string; qty?: number; unit?: string }>;
  sourceTab: "ארכיון_תעודות_גליה";
  sourceRowKey: string;        // פנימי בלבד
};

type MatchStatus =
  | "matched_exact"
  | "matched_by_note_reference"
  | "candidate_review"
  | "order_without_note"
  | "note_without_order"
  | "duplicate_key"
  | "ambiguous"
  | "source_incomplete"
  | "source_unavailable";

type OrderNoteMatch = {
  orderId?: string;
  noteIds: string[];
  status: MatchStatus;
  rule?: "order_to_note_order_id" | "order_note_id_to_note_id" | "customer_date_address_candidate";
  matchedFields: string[];
  warnings: string[];
};
```

### סדר התאמה מחייב

1. **מפתח הזמנה מפורש:** `orders.id === notes.orderId`. ההתאמה נשמרת רק אם מפתח ההזמנה קיים בפועל בשתי הרשומות.
2. **קישור תעודה מפורש:** `orders.noteId === notes.id`. יש לוודא שמספר התעודה ייחודי במקור.
3. **מועמד לבדיקה ידנית בלבד:** מספר לקוח זהה, כתובת מנורמלת זהה ותאריך תואם אם שני הצדדים מכילים תאריך. התאמה זו אינה מספיקה לקביעה אוטומטית שההזמנה והתעודה זהות.
4. שם לקוח, טלפון, נהג, משאית או עיר אינם מפתחות התאמה. אין לבצע auto-match על בסיס שם דומה או תאריך בלבד.

**אזהרה חשובה בקוד הקיים:** ב-`handleGetNotes` שב-`Code.gs`, כאשר עמודת מספר הזמנה אינה נמצאת, הערך `comaxOrder` מקבל fallback למספר התעודה. לכן יש לשמר בשכבת הנרמול דגל `orderIdIsExplicit`; אין להתייחס ל-`comaxOrder` לבדו כהוכחה לקישור להזמנה.

### כפילויות וריבוי תעודות

- אין לבחור את הרשומה הראשונה כשיש שני מזהי הזמנה זהים או שני מספרי תעודה זהים. התוצאה היא `duplicate_key` והפניה לבדיקה.
- הזמנה יכולה להתפצל למספר תעודות. אין לכפות יחס 1:1. יש לאסוף את כל התעודות שקושרו במפורש לאותה הזמנה ולסמן אפשרות לאספקה חלקית.
- תעודה שמכילה כמה מספרי הזמנה תדרוש מודל קשר מפורש או בדיקה ידנית; אין לפצל כמויות על בסיס ניחוש.
- אין להשתמש במספר שורה בגיליון כמפתח עסקי.
- מספרים נשמרים כמחרוזות לכל אורך התהליך כדי לשמור אפסים מובילים ולמנוע שינוי מזהים.

### נרמול

- להפעיל Unicode NFKC, להסיר סימני כיווניות, רווחים חיצוניים ותווי גרש חלופיים.
- מזהים עסקיים: לאחר ניקוי תווים מותר להשוות ספרות כמחרוזת בלבד; אין להמיר ל-number.
- כתובת: להסיר סימני פיסוק ורווחים כפולים ולנרמל קיצורים רק לפי מילון מאושר. כתובת מנורמלת משמשת מועמד ולא מפתח ראשי.
- תאריך: להמיר לפורמט ISO רק כאשר פורמט המקור מפוענח בוודאות. ערך שלא ניתן לפענח נשאר raw ומסומן.
- מק״ט: התאמה מדויקת בלבד. אין להשלים מק״ט מדמיון בשם מוצר.

### איתור חוסרים — הבחנה בין מצב עסקי למצב נתונים

| ממצא | תנאי | הצגה |
|---|---|---|
| הזמנה ללא תעודה מקושרת | כל עמודי ההזמנות והתעודות נטענו במלואם; אין קישור מפורש ואין התאמה חד-משמעית | "לא נמצאה תעודה מקושרת — נדרש בירור" |
| הזמנה שסומנה כסופקה ללא תעודה | תנאי קודם + סטטוס אספקה מאומת שמוגדר במילון סטטוסים | "סומנה כסופקה ללא תעודה — עדיפות גבוהה לבדיקה" |
| הזמנה פתוחה ללא תעודה | סטטוס פתוח/בתהליך | מידע תפעולי, לא חוסר מסמך |
| תעודה ללא הזמנה | אין מספר הזמנה מפורש ואין קישור הזמנה.noteId | "תעודה ללא קישור להזמנה — נדרש בירור" |
| מפתח כפול | יותר מרשומה אחת עם אותו מפתח | "התאמה נחסמה — מפתח כפול" |
| מקור לא זמין/חלקי | timeout, הרשאה, חסר טאב, כותרת חסרה או pagination שלא הושלם | "לא ניתן לקבוע אם חסרה תעודה" |

אין להציג "חסר" רק מפני שפעולת שליפה החזירה מערך ריק. לפני קביעה נדרש לוודא: שני המקורות זמינים, כותרות המפתח נמצאו, כל העמודים נטענו, אין שגיאת parse, וטווח התאריכים/הסטטוסים שנבדק ברור.

### בדיקת פריטים לאחר התאמת הרשומות

- רק לאחר התאמת הזמנה ותעודה לפי מזהה, לבצע השוואת שורות.
- מק״ט מדויק הוא המפתח לפריט; לאחר מכן להשוות כמות ויחידת מידה מנורמלת.
- פקדונות ייבדקו לפי מק״טים מפורשים: 60002, 60060 ו-60006, בהתאם למקור ולמיפוי העסקי המאומת.
- אין להסיק משקל ממוצר על סמך שם בלבד. אם אין משקל במקור/קטלוג מאומת, להחזיר "לא ידוע".
- קיימת פונקציה `buildLogisticsFindings` ב-`src/lib/logistics-audit.ts` שבודקת SKU, יחידות, כמויות ופקדונות; יש להשתמש בה או לאחד איתה את הכללים במקום ליצור מנוע סותר.

## 6. Pagination, טעינה מדורגת ו-cache

- ברירת מחדל לשליפת action: 100 רשומות לעמוד; מקסימום 500. בצ׳אט עצמו יש להעביר למודל תקציר של עד 15–20 רשומות רלוונטיות לכל מקור, לצד total וסטטוס השלמות.
- להשתמש ב-cursor אטום הכולל action, פילטרים, offset/מפתח המשך, זמן snapshot וחתימת שרת. אין לקבל offset או range שרירותי מהדפדפן.
- סדר ברירת מחדל יציב: תאריך יורד ואז מזהה עסקי. כאשר אין תאריך תקין, לשמור סדר מקור ולסמן זאת.
- לבצע lazy-load למקור רק לאחר שה-intent דרש אותו. קריאות לאותו action באותה בקשת צ׳אט יאוחדו.
- Cache: TTL קצר למקורות תפעוליים (למשל 30–60 שניות) וארוך יותר לסיכומים/קטלוג רק לאחר קביעת מדיניות. התשובה חייבת להחזיר `freshness` ו-`fetchedAt`.
- אם המקור אינו תומך pagination ועדיין מוחזר מערך מוגבל, לסמן `completeness: "partial"`. אין להפיק ממנו דוח חוסרים.
- יש להחליף את הטווח הקבוע `A1:AZ3000` בקריאה שמזהה את גבולות הנתונים בפועל או בפונקציית GAS שמחזירה total ועמודים. עד אז יש לסמן את מקור תיק הלקוח כשלמות לא מאומתת כאשר מגיעים לגבול 3,000 שורות.

## 7. הרשאות ואבטחה

1. `API_TOKEN` ופרטי חשבון השירות נשארים בשרת בלבד. אין להעבירם ל-`VITE_*`, ל-localStorage או להודעות המודל.
2. אימות token של GAS מאמת את השרת הקורא, לא את האדם שמחובר לחדר הצ׳אט. יש לאמת role/session בצד שרת לפני חשיפת מידע רגיש.
3. הרשאות מוצעות: מנהל מערכת — כל המקורות; ראמי/סידור — הזמנות, תעודות, איתוראן, לקוחות, בירורים ובקרות; הראל — תמצית תפעולית, אישורים ובירורים; נהג — רק נתוני משימה שהוקצו לו. אלה הצעות מדיניות, לא הרשאות שאומתו בקוד.
4. `getServerLog` מוגבל למנהל/טכני. אין להציג stack traces, tokens, private keys, טלפונים, דוא״ל, קישורי Drive או נתוני זיהוי שאינם נדרשים.
5. רשומות גיליון, הערות, תיאורי מוצר ופניות הן נתונים לא מהימנים ולא הוראות למודל. יש לשמור את הגנת prompt-injection הקיימת ב-`ai.functions.ts`.
6. ה-chat retrieval allowlist כולל קריאות בלבד. חסומים ממנו: `updateOrderStatus`, `saveSignedNote`, `submitApproval`, `submitRamiReply`, פעולות סנכרון/כתיבה, `pollIturanNow` וכל action אחר עם side effect.
7. אין לרשום הודעות שיחה מלאות ללוג שגיאות. יש לשמור requestId, action, זמן, סטטוס, sourceTab וקוד שגיאה ללא תוכן לקוח.

## 8. שגיאות ו-traceability

קודי שגיאה אחידים מומלצים:

- `UNAUTHORIZED` — token או session לא תקף.
- `FORBIDDEN` — למשתמש אין הרשאה למקור.
- `ACTION_NOT_SUPPORTED` — action אינו ברשימת הקריאה.
- `SOURCE_TAB_NOT_FOUND` — הטאב לא נמצא.
- `HEADER_NOT_FOUND` — עמודת מפתח הכרחית חסרה.
- `SOURCE_EMPTY` — המקור נענה אך אין רשומות.
- `TIMEOUT` / `UPSTREAM_HTTP_ERROR` — כשל זמני מול GAS/Google.
- `PARSE_ERROR` — תשובת המקור אינה JSON או מבנה צפוי.
- `PARTIAL_DATA` — לא כל הטווח נטען.
- `DUPLICATE_KEY` / `AMBIGUOUS_MATCH` — לא ניתן לבצע התאמה יחידה.

לכל ממצא התאמה יש לשמור:
- `requestId`, action ושם טאב בפועל.
- זמן שליפה וסטטוס freshness.
- מזהי מקור: מספר הזמנה ומספר תעודה.
- כלל התאמה שהופעל ושדות שהשוו.
- warnings וסיבת אי-התאמה.
- מיקום שורה פנימי לצורכי איתור בלבד, אם המקור סיפק אותו.

תשובת נועה צריכה להבחין במפורש בין "נבדק ולא נמצא", "לא נטען", "נטען חלקית" ו-"נמצאה התאמה". אין להמיר כשל שרת ל-"אין תעודה".

## 9. בדיקות קבלה

1. הזמנה ותעודה עם אותו מספר הזמנה מפורש — `matched_exact`.
2. הזמנה עם מספר תעודה מקושר ותעודה בעלת אותו ID — `matched_by_note_reference`.
3. מספר הזמנה חסר בתעודה והקוד מילא fallback למספר התעודה — לא תיווצר התאמה.
4. מספר לקוח/כתובת/תאריך תואמים ללא מזהה מפורש — `candidate_review`, לא auto-match.
5. שם לקוח דומה בלבד — אין התאמה.
6. מזהה כפול באחד המקורות — `duplicate_key`, לא לבחור רשומה ראשונה.
7. הזמנה אחת עם שתי תעודות מפורשות — להחזיר את שתיהן ולא לסמן כפילות.
8. מקור הזמנות זמין ומקור תעודות לא זמין — `source_unavailable`; אין דוח חוסרים.
9. עמוד שני לא נטען — `completeness: partial`; אין קביעה שאין תעודה.
10. אפסים מובילים במספרי הזמנה/לקוח/תעודה נשמרים.
11. שורת פריט ללא SKU מפורש — אין התאמה אוטומטית לפי שם.
12. בדיקת קריאה בלבד: אין קריאות POST ל-actions של כתיבה ואין שינוי בנתוני גיליון.
13. שגיאת הרשאה, timeout ו-JSON פגום מוצגים בנפרד מתוצאה ריקה.
14. כל תשובה מציינת מקור וזמן שליפה כאשר הנתון תלוי בזמן.

## 10. סדר ביצוע מומלץ

1. **אימות מקור חי:** לקבל snapshot של כותרות הטאבים והרשאות הקריאה. לאמת את שם טאב הקטלוג, PTO, טכוגרף, בירורי הראל ולוגים.
2. **ייצוב actions קיימים:** לפתור כפילות `handleGetOrders_`; לוודא `getNotes` ו-`getOrders` מחזירים מפתח מפורש ו-sourceTab.
3. **שכבת retrieval אחת בשרת:** ליצור מודול TypeScript ייעודי תחת `src/lib` ולהשתמש ב-`createServerFn`; לא ליצור שרת Express נפרד שאינו מחובר ל-TanStack Start.
4. **Intent router + allowlist:** לנתב רק למקורות הדרושים ולחסום כל action כותב.
5. **מנוע התאמת הזמנה–תעודה:** מפתחות מדויקים, כפילויות, ריבוי תעודות, שלמות מקור וסטטוסי חוסר.
6. **שאר מקורות:** להוסיף actions חסרים אחד-אחד, עם חוזה, הרשאה, sourceTab ובדיקות.
7. **בדיקות ואימות פריסה:** להריץ lint/test/build ולבדוק תרחישי מקור זמין/חסר/חלקי מול עותק קריאה של הגיליון.
8. **חיבור למסך:** רק לאחר שהשרת מאומת; להשאיר את UI/UX ללא שינוי ולחבר את הצ׳אט לשכבת השרת הקיימת.

### תנאי מעבר לייצור

לא להכריז "הצ׳אט שולף מכל הטאבים" עד שכל action במטריצה עבר בדיקת חיבור אמיתית, אימות כותרות, בדיקת הרשאות, בדיקת pagination ובדיקת כשל. עד אז יש להציג את המקור כ"לא אומת" ולא כ"מחובר".
